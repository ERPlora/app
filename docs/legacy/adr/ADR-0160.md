## ADR-0160 · Una sola app instalable por plataforma bajo la identidad única `com.erplora.app` — mueren `com.erplora.hub` y `com.erplora.bridge` como identidades de tienda — 2026-07-29

- **Estado:** aceptada (decisión de Ioan, 2026-07-29, en sesión). **Enmienda de DISTRIBUCIÓN a
  [ADR-0159](#adr-0159--bridge-webview-la-app-instalable-renderiza-el-onboarding-del-saas-y-la-pwa-del-hub-en-una-webview-cliente-fino-sin-bd-local--winmacosandroid--2026-07-26)**
  (que ya fijó «el shell ES el bridge» y el reparto Tauri-escritorio/Kotlin-Android; aquí se colapsa la
  **identidad**) y ajusta el plan de tiendas de 2026-07-16 (ADR-0136 + `GOOGLE-PLAY.md`), que preveía
  **dos** fichas por tienda (app + bridge).
- **Contexto.** El plan tiendas heredaba dos artefactos Android: el Tauri-Android de `com.erplora.hub`
  (jobs `check-secrets`/`build-android`/`publish-play` en `tauri-release.yml`, nunca publicado) y el
  bridge Kotlin `com.erplora.bridge`. En Play Console existían **dos fichas en Draft con 0 releases**
  (`com.erplora.hub` 22-jun, `com.erplora.bridge` 16-jul; verificado por Playwright 2026-07-29). El
  package name de Play es **inmutable tras la primera subida** — con 0 releases los drafts aún pueden
  borrarse, así que la ventana para consolidar identidad se cierra con el primer AAB. Además la cuenta
  Play es de **organización verificada** (hub#125 cerrado 07-29) → exenta del requisito de closed
  testing (12 testers/14 días), producción directa. Tras 0159, mantener dos identidades era pura
  herencia: el shell webview y el bridge **ya son el mismo proceso** en Android.
- **Decisión.**
  1. **Identidad única `com.erplora.app`** para la app instalable en todas las plataformas.
  2. **Android = la app Kotlin** (repo `ERPlora-Bridge-android`): shell webview (0159) + bridge Ktor
     en el mismo APK/AAB. `applicationId` → `com.erplora.app`; el `namespace` interno
     `com.erplora.bridge` **se conserva** (R class/paquetes, invisible para Play y usuario). Label
     **«ERPlora»**. El renombrado del **repo** queda pendiente (decisión de Ioan).
  3. **Escritorio = shell Tauri Rust** (`hub/apps/tauri`), `identifier` → `com.erplora.app`.
     **Win+Linux por GitHub Actions; macOS solo build local** (sin cert CI). El **Tauri-Android se
     RETIRA** de `tauri-release.yml` (Android vive solo en el repo Kotlin); muere la Variable
     `PLAY_PACKAGE_NAME_APP`. El binario headless `apps/bridge` **sigue** para el caso
     «PWA en Chrome» (sin cambio; convergencia futura ya apuntada en 0159).
  4. **Fichas:** Ioan borra los 2 drafts y crea **una** ficha `com.erplora.app`. La **primera subida
     del AAB es manual** (registra la upload key — keystore ADR-0053, ahora una sola app); después
     publica el CI del repo Kotlin (tag `v*`, Variable `PLAY_PACKAGE_NAME=com.erplora.app`, track
     `PLAY_TRACK` default `internal`).
  5. **Versionado:** arranca la serie **1.0.0** (`1.0.1`, `1.0.2`… hasta estabilizar). Releases **por
     tag `v*`**, no por push a main (se mantiene ADR-CI 2026-07-10: builds pesados solo con intención
     explícita). `versionCode = major*1e6 + minor*1e3 + patch` → 1.0.0 = 1 000 000, por encima de
     cualquier code previo de ambas apps.
  6. **Cadena «config rápida» (instalar → usar), estado:** instalar la app → onboarding del SaaS en
     la webview (registro → **hub free auto-provisionado**, `provision_free_hub`) → captura de
     `hub_url` (`?shell=1`) → PWA directa en arranques siguientes → hardware auto
     (`IpcBridgeTransport` en Tauri / `WsBridgeTransport` + FGS en Android, con autoarranque tras
     reinicio — android#13). **Accesos de lanzamiento por canal:** NSIS = Escritorio + Menú Inicio
     (default del template Tauri v2) · MSIX/Store = Menú Inicio (convención Store) · `.deb` = entrada
     de menú (`.desktop`) · AppImage = portable, sin instalación (canal secundario de QA) · Android =
     icono launcher. **Validación pendiente en el primer build real de CI (v1.0.0).**
  7. **SaaS:** `GOOGLE_PLAY_BRIDGE_ID` → **`GOOGLE_PLAY_APP_ID`** (= `com.erplora.app`); todos los
     redirects 302 de Android (saas#707) apuntan a la **misma ficha**.
  8. **Microsoft Store: también UNA sola ficha «ERPlora»** (aclaración de Ioan, misma sesión: «no hay
     una segunda app — la app es simplemente ERPlora, el antiguo bridge, con interfaz de configuración
     rápida, y al abrirse abre la PWA del hub»). La sección «Segunda app: ERPlora Bridge» de
     `MICROSOFT-STORE.md` se elimina; el headless `apps/bridge` **no publica en ninguna Store** (solo
     S3 `downloads/bridge/`, caso «PWA en Chrome»). En el SaaS, `MICROSOFT_STORE_BRIDGE_ID` →
     **`MICROSOFT_STORE_APP_ID`** (mismo tratamiento que el de Play).
- **Consecuencias.** + Un solo install, una ficha, una review de Google, una upload key, un solo
  `publish-play`. + El usuario ve UNA app «ERPlora» (la promesa de 0159 sin la incoherencia de marca
  «Bridge»). − El nombre del repo `ERPlora-Bridge-android` deja de reflejar su rol (renombrar =
  pendiente, Ioan). − Cambiar el `identifier` de Tauri cambia el directorio de datos de la app
  (pre-lanzamiento, 0 usuarios instalados → sin migración).
