## ADR-0033 · El asistente AI es una capacidad CORE del Hub, no un módulo de marketplace — 2026-06-13
- **Estado:** aceptada (supera, **solo para el asistente**, la parte pendiente de [ADR-0032](#adr-0032--monetización-de-módulos-2-tier-freepremium--capa-gratuita-y-trials-declarados-en-modulejson--2026-06-13) que pedía publicar la fila `Module` del asistente y migrarlo a `ModuleTier`; WhatsApp se mantiene como premium-módulo bajo ADR-0032)
- **Contexto:** el asistente estaba **etiquetado** como módulo premium (capa gratis + de pago), pero esa etiqueta contradecía al código y al concepto. Contrastado contra los cinco ejes que el propio sistema usa para distinguir módulo de core, el asistente es core en los cinco: (1) es **horizontal** — trabaja *sobre* todos los módulos instalados (lee sus bloques `ai:`, despacha a sus `@action`, indexa sus docs al RAG), no es un vertical de negocio; (2) **no tiene artefacto instalable** — el proxy de chat está horneado en el binario Rust (`hub/crates/server/src/assistant.rs`) y el RAG vive en `hub/apps/ai/knowledge/`; no hay `module.zip`, migraciones ni install real; (3) **no es opcional/desinstalable** — "desinstalarlo" no quita código del binario; (4) **no tiene tablas/dominio propio** de negocio — los datos que toca son de otros módulos; (5) su **UI es global** (✨ del topbar), no un tab dentro de la nav de un módulo. Además, ADR-0032 admitió que la fila `Module` del asistente **ni existe** en Aurora (verificado 2026-06-13), o sea seguir la vía módulo exigía publicar un módulo-fantasma sin artefacto.
- **Decisión:**
  1. **El asistente se formaliza como capacidad core del Hub**, siempre presente por defecto (✨ del topbar), sin paso de descubrir/instalar y fuera del catálogo de marketplace. La capa de ejecución no se mueve (ya está donde debe): proxy Rust + RAG local + orquestación multi-LLM en Cloud (`saas/apps/assistant/`); el Hub sigue sin hablar nunca con LLMs.
  2. **Conserva su billing propio per-app** — `AssistantTier` (free 30 msgs / basic / pro / enterprise) + `AssistantUsage` + `check_quota` en el proxy Cloud. Eso ya implementa el modelo de coste decidido: **capa gratis con tope duro + upgrade de pago** (Q2). **No** se migra `AssistantTier`→`ModuleTier` ni se publica fila `Module`.
  3. **Se desacopla del sistema de módulos:** el binding de tier de pago deja de ridar sobre `ModulePurchase.assistant_tier`; `get_hub_tier()` resuelve el tier activo del asistente sin pasar por el marketplace/entitlement de módulos. `is_module_entitled` deja de ser camino del asistente.
  4. **El upgrade es una suscripción del propio asistente**, expuesta desde el endpoint que ya existe (`GET /api/v1/hub/device/assistant/config/`, que devuelve tier+cuota). El flujo de pago/precio del upgrade y cualquier toque al modelo de comandos/runtime Rust son **columna del humano** (preguntar, no decidir).
  5. **Justificación del billing metered:** el coste del asistente es **por tokens**, que encaja mal con la suscripción plana de módulo; `AssistantTier/AssistantUsage` es la primitiva correcta para uso medido y ya existe.
- **Consecuencias:** modelo más honesto (lo que ya es en ejecución/UI/concepto queda reflejado); se elimina la necesidad de un módulo-fantasma en el catálogo y de casos especiales en `is_module_entitled` para "un módulo siempre presente". Negativo: hay que **desacoplar** el tier del asistente de `ModulePurchase` (hoy enredado) y construir una pequeña superficie de upgrade propia (suscripción del asistente). **No aplica a WhatsApp** (vertical instalable real → sigue módulo premium por ADR-0032). La promesa comercial "capa gratis con tope + upgrade" se mantiene intacta, solo cambia de "comprar módulo" a "ampliar uso del asistente".
